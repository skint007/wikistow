# Reading and editing pages offline

Without a connection, WikiStow shows nothing. The browser app doesn't load, and the desktop app can't open a page it showed a minute ago. This ADR decides how both apps read and edit offline (#242): what a device keeps, how it is sealed, how the vault opens with no server, and how changes made offline meet the server's.

In short:
- **What's kept.** The desktop app keeps every page the person can see. The browser keeps the pages they open, and every page if they turn that on. A kept page has its published version and, for someone who can edit it, its draft, with the images they show. The device also keeps the trees, so the sidebar works.
- **Sealed for this person.** Everything kept is sealed under a key derived from the person's identity key, as the desktop search index is (`sealOnDevice`), so only their unlocked vault opens it. The desktop keeps it in files, the browser in IndexedDB.
- **Unlocking offline** uses a kept copy of the vault wrapper with the passphrase, or the remembered unlock where it's on. The session opens from a kept copy of the contacts record.
- **The browser** gets a service worker that serves the app when the server can't, and a web app manifest, so it can be installed on phones.
- **Offline changes**: drafts, new pages and new folders wait on the device, sealed, and go to the server in order when it answers. Each names what it was based on, so a page changed meanwhile comes back as the usual conflict. Everything else that needs the server waits for it, and the app says so.

## What the code supports today

- **The desktop keeps its search index** in `search-index`, sealed by `sealKept` (`packages/client/src/operations/search.ts`) under a key from the identity key, bound to the account, installation and app build (#3). Each indexed page holds its revision ID, title, reduced text and properties. It is one file, written whole (`keptFile`, `apps/desktop/src/kept-file.ts`). #238 adds each page's resolved links. A browser keeps its index in memory only.
- **The desktop keeps its trust marks** in `trust-marks` (`KeptMarks`, `packages/client/src/kept-marks.ts`): the contacts mark, the No going back marks and the last restore seen. Only the mark is kept, not the record. The browser keeps them for one session.
- **Opened versions** stay in memory only (`RevisionCache`, `packages/client/src/revision-cache.ts`), and lock clears them.
- **Unlocking needs the server three times.** `openVault` reads the wrapper (`GET /api/vault`). `openSession` reads `GET /api/installation` and the contacts record. The browser's remembered unlock (#115) also asks the server for the vault's version before it opens (`restore` in `packages/ui/src/vault/open.ts`), and with no answer it leaves the vault locked. So even a remembered unlock doesn't open offline today. Before any of that, `_app` reads `meQuery`, and with no answer the route fails.
- **Saves are sealed with the share's current keys.** `saveDraft` and `createPage` wrap the content key under the share's current key version and send the permission version (`commitFor`, `withFreshKeys`). Either may move while a device is offline. The issue's note that "the bytes can be sealed before upload" holds for attachments: their AD binds only installation, space, page, audience and attachment ID (protocol section 5.3). It doesn't hold for revisions, so this ADR seals them when they are sent.
- **Clients make page, folder, revision and attachment IDs** (`newId`). A second `createPage` or `createFolder` with an ID already used is refused as `duplicate`, and a save names its base, so a sent change can be told apart from one that never landed.
- **The conflict view** exists: a save over a draft someone else saved is `stale-head`, and the draft view offers **Save mine on top** or **Discard mine and view theirs** (`DraftSession`, `page/draft-editor.tsx`).
- **The security policy** already allows a same-origin worker and manifest (`worker-src 'self'`, `manifest-src 'self'`, `packages/contracts/src/security.ts`). The server sends `index.html` for any app path and caches `/assets/*` forever (`apps/server/src/http/static.ts`). There is no service worker and no manifest.
- **The live tree** (`GET /api/me/tree-changes`) says which spaces changed, and the index lists those again. Pages a space no longer lists leave the index. #240 adds a trash: a deleted node leaves every listing and can't be opened, so the index drops it with no change.

## Decisions

### 1. What's kept

- **Pages.** For each kept page: its current published version, and, where the person can edit it, its current draft, each as opened (`OpenedRevision`: the decrypted payload with its title, Markdown, attachments, cover, properties and link table). Older versions aren't kept, and neither is a version this app can't read (`newer-format`), so an updated app opens it from the server. The images a kept version shows (body images, banner, page or folder image) are kept with it. Other attachments are kept once opened on the device.
- **Which pages.** One setting, **Keep for offline**, with **Every page** and **Pages I open**. The desktop starts on Every page, and the browser on Pages I open (decided on #242). Pages I open keeps a page the first time it opens, in the reader or the draft view, and keeps it current from then on (decision 3).
- **Structure.** The space list and order, Shared with me, each space's tree with its folders' names and looks, the labels and heads of the kept pages, and the IDs of the others with no title, as last loaded. So in Pages I open the sidebar offline shows the folders and the kept pages only, and no title of a page never opened on the device is kept.
- **For unlocking** (decision 5): the vault wrapper, the last `/api/me` answer, the installation ID, and the contacts record as last accepted, with the trust marks.
- **The search index**, with Every page only (decision 9).
- **Offline changes** (decision 7).

Settings, under **This device**, shows the choice, how much is kept ("1,204 pages, 312 MB"), and: "Pages stay readable on this device after someone removes your access, until the app is back online." On a desktop without a keyring the choice is off, with "Needs a keyring to keep pages between launches" (decision 2). Choosing Every page in the browser, or making the first offline change there, asks the browser to keep the site's storage (`navigator.storage.persist()`). Choosing Pages I open drops pages not opened on this device.

### 2. How it's sealed and stored

- **One sealed item per thing kept.** Each version, tree, attachment and offline change is its own item, written once or replaced whole, so keeping a page never rewrites the rest. Versions never change, so a kept one is written once.
- **Sealing.** `sealOnDevice` under a new key domain, `kept-key/v1`, with the AD `canonical('kept/v1', [installationId, identityId, name])`. Binding the item's name means a file can't stand in for another. Item names are `deviceTag(identity, 'kept-names/v1', <kind and ID>)`, so a listing of what's kept shows no IDs. Attachments are kept as the server serves them, already encrypted under their own keys, which only the sealed versions hold.
- **Not bound to the build.** Kept versions hold payloads, not text reduced for search, so a new app version reads them as they are. They are bound to a format version in the AD instead. The index stays bound to the build (decision 9).
- **Unsealed**, since they are needed before unlocking and hold no content: the setting, the last `/api/me` answer and the installation ID, and the vault wrapper. The wrapper is what the server keeps: the vault key under the passphrase's Argon2id key, and under the recovery key. With it, someone who has the device can guess the passphrase offline, as someone with the server's database can.
- **Where.**
  - Desktop: a `kept` folder in the data folder, beside `search-index` and `trust-marks`, one file per item, mode 600, written to `.next` and moved into place as `keptFile` does. The bridge gains read, write, remove, list and clear for it, and main accepts only base64url names, so no name leaves the folder. As today, pages aren't kept on disk without a trusted keyring: the app keeps what that launch opened in memory, as Pages I open would, so a lost connection still works until it quits. The queue is the exception: offline changes go in the `queue` folder with or without a keyring, sealed under the identity key, which the keyring never held, and a launch without a keyring leaves it alone, so changes are never lost to a keyring that didn't open.
  - Browser: one IndexedDB database, `wikistow-kept`, holding the items, with the unsealed ones beside them. Tabs share it.
  - In both, offline changes are in a store of their own (a `queue` folder on the desktop), and the account ID and name that everything kept belongs to are kept unsealed beside them, so the app can tell whose they are before anyone unlocks, and warn before a sign-in to another account deletes them (decision 10).
  - Both through one `KeptStore` interface in `packages/client`, with a memory store for tests and the keyless desktop.
- **The browser keeps its trust marks** in the same database (`KeptMarks` over an IndexedDB `KeptFile`), since the offline session needs the contacts record and keeping the record without its mark makes no sense. The record goes in the same sealed item as its mark, on the desktop too, so the two never disagree. Browser tabs write that item under a Web Lock, reading it again first and keeping the higher of each mark with its record, from marks taken since the same restore (`restoredAt`), so one tab never writes back another's older marks. So the browser then detects a contacts rollback, and keeps its No going back marks, between sessions as the desktop does (protocol sections 6.8, 8.5 and Q2).

### 3. Keeping it current, and letting go

- **One keeper** in `packages/client`, run by the app after unlocking and after each index update, while online. Its scope is every page (Every page) or the pages already kept (Pages I open). It compares each listed page's heads with the kept ones and opens only versions it doesn't hold, in the batches the index uses (`fetchRevisions`, `openRevisions`). It reads the versions the index just opened from memory first, so nothing is downloaded twice, and the index's first build reads kept versions before the server. Progress shows in Settings ("Keeping pages for offline: 120 of 1,204").
- **It follows the live tree.** A change heard on `tree-changes` lists that space again, as for the index, and the keeper follows. A version replaced is dropped, with images nothing else kept shows.
- **Letting go.** At each listing, pages the space no longer lists are dropped, with their versions and attachments, except the base version and attachments an offline change still needs (decision 7), which go once it is resolved. A space no longer listed goes whole. That covers a page deleted, moved to another space, or put in the trash (#240), and access removed or lowered: a reader's kept drafts go when their role drops. `refreshAccess` runs the keeper over a fresh listing.
- **Until then**, what's kept stays readable on the device, sealed, as the setting says. If the device never comes back online it stays readable to whoever has the device and the passphrase, as anything already downloaded does (protocol A3).

### 4. Offline and back online

- **Offline** means a request got no answer, or a 5xx answer that isn't the server's own JSON error, as a proxy or tunnel gives when the server behind it is down (Cloudflare's 521 to 530 among them). A server's own refusal isn't offline: a signed-out answer still goes to sign-in. A home server that's down often drops packets rather than refusing them, and the system then waits a minute or more, so API reads give up after 10 seconds without an answer (the response's headers), and the reads before the vault opens (`/api/me`, the vault, the installation, the contacts record) and the probe after 5. Writes keep no deadline of their own, since a share or a large save can take longer to send, but once the app is offline a write still waiting is given up, as a lost answer (decision 7). Uploads, downloads and the AI stream keep their own limits.
- **While offline**, reads come from what's kept, without trying the server for each. The app tries `GET /api/installation` every 30 seconds, when the browser says it is online again, and when a tab or window is shown again. The first answer ends offline. The UI's queries use `networkMode: 'always'`, so TanStack Query doesn't pause them when the browser thinks it's offline.
- **What the person sees.** The rail (the top bar on phones) shows an **Offline** pill, with a hint: "Showing what this device kept, as of 14:05. Changes are saved on this device and sent when you're back online." The time is when the app last heard from the server. A page shows "As of <time>", from when its space was last listed. A page not kept opens to "This page isn't kept on this device", with the setting named. A link through a link table to a page not kept reads as not kept, rather than missing, and the draft view doesn't offer **Create this page** for a missing link while some of the space's pages aren't kept, since the link may name one of them.
- **Back online**, in order: the steps an offline unlock skipped (decision 5), then a fresh listing of every space, as after a tab comes back into view, then the offline changes (decision 7), then the index and the keeper.

### 5. Unlocking offline

- **Before the vault.** `_app` takes the kept `/api/me` answer when the server doesn't answer, and goes on offline. A kept answer for another account isn't used.
- **The wrapper.** Every online unlock keeps the wrapper and its version, replacing an older one, and so does a passphrase change made on this device (`changeVaultPassphrase`, as after a recovery). Offline, the passphrase unlocks against it, in the vault worker as now. A wrong passphrase offline adds: "This device last unlocked online on 3 November. If you changed your passphrase since, use the one from before." The recovery key's page sets a new passphrase before the session opens, which needs the server, so recovery waits for it.
- **The remembered unlock.** The browser's (**Remember on this browser**) and the desktop's (**Remember on this computer**) open offline as online. The browser skips its check of the vault's version when the server doesn't answer, and makes it once it does (below). Turning on Remember offline takes the version from the kept wrapper.
- **The session.** `openSession` opens from the kept installation ID and contacts record, checked against the kept mark as a served record is (protocol section 8.5), and stops if it fails. Nothing is signed offline, and nothing is wrapped under a folder key: revisions are sealed when sent (decision 7).
- **Back online**, the app runs what the offline unlock skipped: `GET /api/installation` (another installation ID ends the session, since nothing kept opens for it; a restore not seen shows its notice and starts the marks over, as now), the vault's version, and the contacts record against the mark. A vault version newer than the one the device unlocked against means the passphrase changed elsewhere: the app replaces the kept wrapper, forgets a remembered unlock, and locks as Lock vault does, once the draft being typed is in its entry, so the new passphrase is asked for. Offline changes stay queued, sealed.
- **The desktop.** With a trusted keyring it keeps its session, so it starts offline into the unlock page, or the remembered unlock. A start with no answer from the server counts as offline, not signed out. Without a keyring each launch signs in through the browser, so it can't start offline.
- **What this means.** After a passphrase change made elsewhere, the old passphrase, or an unlock remembered before it, still opens a device's vault offline, until that device is back online and locks (protocol A13). The recovery key's note in `wikistow.md` (an attacker holding an older wrapper) already covers the rest.

### 6. The browser app shell

- **A service worker**, `/sw.js` at the top of the site, written for this app (about 100 lines), built with the web app, with the build's file list put in at build time. The desktop doesn't register one: its app is on disk already.
  - At install it caches `index.html`, `boot.js`, the icons, the manifest and every file under `/assets` in the build, lazy chunks and workers included, so the editors, the Argon2id worker and the reader's worker load offline. It leaves out source maps (`*.map`, about half of `/assets`) and what only the Workshop uses (`esbuild.wasm`, 14 MB), since Workshop drafts need the server. It also leaves out the diagram frame's files (`/assets/diagram/`, Mermaid's 5.5 MB among them): the frame is sandboxed, so its navigation and requests never come to the worker (found building step 4, checked again for #333). Instead the worker fetches them once as it installs, keeping no copy, into the browser's own cache, which does answer the frame offline since their names carry hashes and they're sent `immutable` (ADR 0010, decision 6). Until #333 the frame's page and script were outside `/assets`, sent `no-cache`, so diagrams didn't draw after an offline reload.
  - **App pages** (navigations to an app path), and the files at the top of the site that it cached (`/boot.js`, the icons, the manifest), whose names carry no hash: the server first, and the cached copy when there's no answer within 3 seconds, or the answer is a 5xx that isn't the server's own (decision 4). Cached responses keep the server's headers, so the security policy is the same.
  - **`/assets/*`**: from the cache, else the server.
  - **Left to the server**: `/api/*`, public pages (`/p/*`), `/plugin-host.html` and its files, and any other path with an extension that it didn't cache. The diagram frame's requests never come to it.
  - **Updates.** A new worker takes over at once (`skipWaiting`, `clients.claim`) and drops the old cache. So online, the app loads exactly as today; offline, it loads the build last cached. A tab left open on the old build can't then load a lazy chunk it hadn't loaded yet, as after a deploy today; reloading fixes it.
- **A manifest**, `/manifest.webmanifest`, linked from `index.html`: name WikiStow, `start_url` and `scope` `/`, `display: standalone`, Midnight slate's colours, and 192 and 512 pixel icons (plain and maskable) made from `favicon.svg`. Served as `application/manifest+json`. With the worker, phones can install the app.
- **Storage limits.** Safari deletes a site's storage after seven days without a visit unless the app is on the home screen, and an app on the home screen has storage of its own. So on iPhone and iPad, Settings says to add WikiStow to the home screen before relying on offline, and that changes made in Safari are sent only from Safari. Browsers may clear storage they weren't asked to keep (decision 1). Pages a browser clears come back from the server. Offline changes can't, so the first one asks for persistent storage (decision 1), and the Offline pill says changes are only on this device until they're sent.

### 7. Offline changes

- **What can be made offline:** drafts of kept pages (title, Markdown, properties, cover, attachments, through the draft view), new pages, and new folders. The draft view says "Saved on this device" where it says "Saved".
- **The queue.** One on the device, for the account the kept account ID names, in its own store (decision 2), each entry sealed like any kept item. Entries hold what the person made, in plaintext before sealing, never a sealed revision:
  - **New folder**: its ID (`newId`), space, parent and name.
  - **New page**: its ID (`newId`), space, parent, and its payload.
  - **Draft**: the page, the draft it was based on (the kept draft head), and the payload.
  - Attachments added offline are sealed for the page's draft at once (`sealAttachment`; protocol section 5.3) and kept with the entry until its save lands, so the payload names their refs. A later save of the entry uploads them again first, since the server sweeps staged uploads after a day.
- **One entry per page.** Saves of the same page replace its entry's payload and keep its base, and count up the entry's local version; edits to a page made offline update its New page entry. A save checks its base as the server would: one over an entry another tab or window made is a conflict there and then, so two tabs never overwrite each other. Tabs hear of each other's changes to the queue on a `BroadcastChannel`.
- **The device as the head.** Offline, the page's draft is its entry: the reader shows "Changed on this device, not saved yet", search indexes the entry as it does a saved draft, and a page made offline shows in the sidebar, marked, under its parent, which may be a folder made offline.
- **Sending.** In order, one sender at a time (a Web Lock in the browser), through the same operations as online, which seal with the share's keys of the moment, check the region and resend after `key-version` or `region-mismatch` as now. A page waits for the folder it's in. A draft's attachments go up just before its save. Uploads need the page to exist, so a New page with attachments is made first without them, and without an image banner or icon, then saved again with them, as `createFromTemplate` does. Those are two steps, each recorded on its own, and the entry goes only after the last.
- **Lost answers.** Before each request the entry records the IDs it uses (a folder's ID, a page's ID and its first revision's, or a draft's revision ID, which `commitFor` takes) and the local version it carries, and keeps that version's payload until it is known to have landed. A draft view's own save that got no answer is recorded on its entry the same way, and every session with the page counts the recorded ID as its own, so the live tree naming it as the head isn't a conflict. The next send resends that same version under the recorded ID. The server answers `duplicate` for an ID already used, even when sealed again (`replayed`), so that answer means the recorded version landed: the entry is based on it, and goes if nothing was saved into it since, or is sent again on top of it with a new ID. IDs are random, so only this device used them, and the person's own save never comes back as a conflict.
- **An open draft view.** While its page has an entry, the draft view's session saves into it, online too, until the sender has sent it. When the sender reaches that page, it sends the entry's latest text. Once it lands, the entry goes only if its local version is the one sent; one saved into meanwhile is based on the revision that landed and sent next. Every tab's session with the page takes the landed revision as its base, as after its own save, so typing meanwhile saves on top of it as usual. The same holds for a page made offline: its New page entry is sent, and the session then saves over the page's first draft.
- **A conflict.** A draft whose base isn't the draft head any more is `stale-head`. The entry stays, and a note in the shell lists the pages waiting ("1 page changed while you were offline needs a choice"). Opening one opens the draft view with the entry's text as the unsaved changes and the usual prompt: **Save mine on top** or **Discard mine and view theirs**. Nothing is merged and nothing is overwritten without the person's choice.
- **A page gone, or out of reach.** `not-found` or `forbidden`: the page was deleted, moved to another space, put in the trash (#240), or access was lost. The entry stays, listed with "This page was deleted, or you lost access to it, while you were offline", and these choices: **Try again**, for a page an owner has since restored from the trash; **Save as a new page in my space** (the person's home space, with the entry's title, text and the attachments the device has, sealed again for the new page; any it doesn't have, such as a file never opened here, are named in the dialog and left out), **Copy text**, or **Discard**. A page an owner later restores from the trash comes back as it was, without the offline edit. A folder made offline whose parent is gone fails the same way, and the pages made in it offer the same choices; empty folders made offline just go.
- **Other refusals** (too large, a page limit) leave the entry listed with the server's reason and **Try again**. A network failure leaves the queue to try again when the server answers. Entries after one that stops still go, unless they need it, as a page needs its folder.
- **Quitting or closing** with entries not yet sent is safe: they are on disk, on every desktop and in every browser.

### 8. What waits for the server

Everything else, and the control says "Needs the connection" (a `data-hint`) rather than failing: publishing and unpublishing, ticking tasks while reading (which publishes), editing a query table's cells, public links, sharing, members and groups, moves and copies, deleting and the Trash, renaming a folder or changing its look, new spaces, templates, history and restoring a version, agents and the chat assistant, browser plugins (the desktop's run from disk), export, Settings that the server stores, signing in, and signing out (except the desktop's **Sign out on this computer**, decision 10). Offline, Lock vault seals everything kept until the next unlock. Back online, Publish, restoring a version, and moving or copying a page wait until the page's offline change is sent, so they never act on the draft from before it. A folder made offline isn't offered as a place to move, copy or publish into until it is sent (#297), as the server doesn't have it yet.

### 9. Search, Linked from and query tables

- **Search** works over what's kept, with the filters as online. Online, the index covers every page the person can read, so only Every page keeps it: the browser then seals it by `sealKept` in IndexedDB, like the desktop's file, bound to the build. In Pages I open the index stays in memory, in the browser as now and on the desktop too, which then stops writing `search-index`; offline it is built from the kept versions alone. When the build changes, or nothing was kept, it is built from the kept versions with no server, so an offline browser on a new build still searches.
- **Linked from (#238)** and query tables read the viewer's index, so offline they show the kept pages, as the index has them. In Pages I open that is only pages opened on the device. #238's resolved links go in the index, which this ADR keeps as #238 defines it; offline changes go in as written, as a save does.
- **The trash (#240)** needs nothing here: trashed nodes leave the listings, so the keeper and the index let them go at the next listing.

### 10. Locking, signing out and signing in

- **Lock** clears what's decrypted in memory, as now. Everything kept stays sealed.
- **Sign out** needs the connection. Before it does anything it warns when offline changes haven't been sent: "2 changes you made offline haven't been saved yet. Signing out deletes them." It tells the other tabs on the `BroadcastChannel`, which lock and stop keeping and sending, then deletes everything kept: pages, attachments, trees, the index, the queue, the trust marks, the wrapper and the `/api/me` answer. Every tab closes its connection to the database when another asks to delete it (`versionchange`), so a second tab can neither hold the deletion up nor write again after it. The service worker's cache holds only the app's files, so it stays.
- **A server that's gone** (#257): no answer, a 404 from `/api/me` or the sign-out route, or an answer that isn't WikiStow's JSON, as when its host moved and a proxy answers every path. The desktop app's error screen, and its sign-out when the sign-out route gets one of those answers, offer **Sign out on this computer**. It forgets the session, the vault and the server chosen (`config.json`), and deletes everything kept, as a sign-out does, then asks for a server. The error screen offers it for a server error (5xx) too, beside **Try again**; a sign-out that gets WikiStow's own refusal, a 5xx among them, leaves the session as it is. The server's session stays alive until it expires or is revoked from another device, and the screen says so. The offline-changes warning above comes first here too. A browser tab only offers **Try again**: its session cookie is the server's to end. Once offline unlock is built, a start with no answer, or a proxy's 5xx, opens offline instead (decision 5), so the screen stays for the other cases, and offline the desktop's **Sign out** offers **Sign out on this computer** in place of "Needs the connection" (decision 8), so a server that never comes back still has a way out.
- **A session the server ended** (a revoke, a suspension, a password reset, or a session that lapsed unused, which the app can't tell apart) goes to sign-in as now, and everything kept stays, sealed. A sign-in to the same account takes it up again, sends the queue, and the next listing drops what its access no longer covers (decision 3).
- **Signing in** to another account deletes everything kept. When the queue holds changes not yet sent, the sign-in page says so first, by the kept account's name ("This device has 2 changes Sam made offline that haven't been saved yet. Signing in as someone else deletes them."). What's kept for the same account stays. So the desktop's main process stops deleting the `kept` folder at every new sign-in, as it does `search-index` and `trust-marks` today (`linkArrived`, `apps/desktop/src/main.ts`): the pages delete it once the `/api/me` answer names another account.

## Out of scope

Agents and the CLI, which stay online; merging edits (#334); keeping older versions or history; offline publishing, sharing, moves, deletes, renames of folders (#330, #331), new spaces and templates; background sync while the app is closed (the browser's Background Sync API); a storage cap.

## Considered options

- **Put the pages in the search index file.** One file written whole, bound to the build, rewritten on every change: a new release would download every page again, and a large wiki would rewrite megabytes per save. Rejected for decision 2's items.
- **Keep the server's answers as they came** (ciphertext responses for each route) and replay them offline. Operations would run unchanged, checks and all, but what's kept would be as wide as the routes, mixed in time, and every open would decrypt again. Rejected for kept decrypted versions, sealed.
- **Seal offline revisions at once.** The issue suggested it. A key rotation or a permission change while offline would make every queued save fail, and a move would change its region. Sealing at send time keeps every server check as it is, and attachments, whose AD names no share, are still sealed at once.
- **vite-plugin-pwa (Workbox).** Standard, but brings a large dependency for about 100 lines. Rejected for a small worker of the app's own.
- **Keep the browser on its cached build until every tab closes**, the default lifecycle. It would leave people on old builds online. Rejected for taking over at once, which matches today's loading.
- **A third conflict choice, "Keep both" as a separate page.** It would never lose either edit, but adds a choice to the conflict view for every save. Rejected on review (below).

## Consequences

- `wikistow.md` gains an **Offline** section, and offline leaves the later work in Agreed first version. As they land, the build PRs change Human and agent keys (the kept wrapper), search (the index kept with Every page only, in the browser too), and Desktop and CLI (the `kept` and `queue` folders). The protocol gains A13 and notes in sections 6.8, 8.5 and 17 (Q2). Step 5 also changes A2, A4, A5 and A6, which say the browser keeps no marks between sessions. `CONTEXT.md` gains **Kept for offline** and **Offline change**. Each build PR updates the text for what it builds.
- `packages/client` gains `KeptStore`, the keeper, the offline session and the queue. `packages/ui` gains the connection state, the setting, the pill and the queue's note. The desktop bridge gains the `kept` folder. The web app gains `sw.js` and the manifest. The server changes only to serve the manifest's media type.
- `leak.spec` gains the new storage: `wikistow-kept` while open and after a lock, holding none of the test's markers readable, and gone after sign-out. Today it expects Cache Storage to be empty; step 4 lets it hold the service worker's cache of app files, by name, before and after sign-out.
- A browser that used only memory now writes sealed content to disk by default, for the pages a person opens. Decided on #242.
