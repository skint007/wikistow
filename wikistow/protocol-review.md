# WikiStow protocol review log

This log records the focused security review of [`protocol.md`](protocol.md). `wikistow.md` L333 and L357 require that review before the protocol is final, and before any production rollout. For Milestone 2 it is a series of adversarial review rounds, each with a different brief. Every finding is logged here with its outcome.

## How rounds run

1. **Each round runs three briefs** against the current text of `protocol.md`, together with the code it describes.

   | Brief | Prefix | Focus |
   |---|---|---|
   | server | `S<round>-n` | **Malicious server or operator.** Forks, rollback, omission, key substitution, reordering, relabelling, withheld bodies, inserted grant rows, replayed records, and the M1 backfill. |
   | member | `M-n` through round 6, then `M<round>-n` | **Malicious or removed member, or a compromised agent host.** Escalation through grants, groups, ownership and agent grants. What a removed member keeps. An agent outliving its human's access. Abuse of enrollment and lookup codes. A non-owner endorsing a forged log. |
   | encoding | `Fn` (High and Medium), `Ln` (Low); from round 2 logged as `E<round>-Fn` and `E<round>-Ln` so IDs stay unique. Rounds 7 and 8 used `E<round>-Mn` (Medium) and `E<round>-In` (Info), logged as given | **Encoding pitfalls.** Domain separation, length prefixes, field order, number and string encoding (including lone surrogates), base64 strictness, signature and hash malleability, and the fact that sealed boxes don't authenticate their sender. |

   Round 1 ran the three briefs in parallel, as three independent reviewers. Round 2 and later rounds repeat all three, and may add a new brief a round suggests.
2. **Reviewers** are independent subagents. Each gets only its brief, `protocol.md`, and the code paths it names. A reviewer reports findings with:
   - a severity;
   - a concrete attack or failure;
   - the section it breaks.
3. **Triage.** Each finding keeps the ID its reviewer gave it, with the prefix above. The **Round** column says which round found it. Each gets an outcome:
   - **fixed**, with the protocol.md section or commit;
   - **accepted**, recorded as a residual risk or open question in protocol.md;
   - **rejected**, with the reason.

   A finding can be partly fixed and partly accepted; the outcome says which part is which.
4. **Stopping rule.** Rounds continue until one finds nothing high or critical. Then the identifiers in protocol.md §3.5 are frozen, and protocol.md's status changes to frozen.
5. **Later changes.** After freezing, any change to a frozen format needs a new domain version and a new entry in this log.

## Severity

| Severity | Meaning |
|---|---|
| Critical | Plaintext, a content key or a secret key reaches someone outside the intended audience, or an attacker gains authority over a space, without any user mistake. |
| High | Same as critical, but needing an unusual precondition, or a user mistake the interface invites. Also: an attack that goes undetected on a property protocol.md says is detected. |
| Medium | An integrity or availability break with no confidentiality loss, or a metadata leak beyond residual risk R3. |
| Low | A hardening, clarity or consistency issue. |
| Info | A note with no security effect. It doesn't count toward the stopping rule. |

## Change of design (2026-10-05)

On 2026-10-05 the project owner replaced the Milestone 2 design that rounds 1 to 16 reviewed. The signed, hash-chained access log per space had grown too complicated to build and explain: owner vouching, endorsed prefixes, high-water marks, read-only spaces, re-homing and `close`, node placements and owner requests each answered a real finding, and together they made a protocol few people could follow. He asked for something "secure, but not overly complicated, like Joplin".

The new design (protocol.md, sections 6 to 11):

- **Folder keys.** Each shared space or folder has its own versioned key set: a draft key and a published key. Each revision's content key is wrapped with one of them. Readers get only published keys. Content outside every share stays sealed to the space's owners, as in Milestone 1.
- **Spaces and folders only.** No page grants, and shares don't nest.
- **Only owners seal folder keys**, during Share, Remove or adding a co-owner, to the people shown in the dialog. Saves never choose recipients. A person's own app seals keys to their own agents.
- **No safety codes.** Each app pins the first key it sees for each person, and warns and stops sharing when that key changes.
- **Removal rotates the keys.** The new key version goes only to the people who held the previous one, minus the removed person, and the server refuses saves under the old version.
- **Groups are deferred** to a later milestone (#30).
- **Accepted risks** (protocol.md §2.4). A malicious or breached server can ignore role rules, hide or roll back changes undetected, and keep serving a removed person data they could already decrypt. It can't read content, add a reader by itself, or decrypt anything saved after a removal. Keys are trusted on first sight, so a server can substitute a key before any app has seen the real one.

**What still applies from rounds 1 to 16.** Findings and outcomes about parts this design keeps still stand: the primitives and encodings (protocol.md §3), records and their key commitment (§5), the contacts record format (§8.1), agent enrollment and credentials, and the CLI's output rules (§9).

**What no longer applies.** Findings and outcomes about the access log, its replay and redaction, vouched keys and the endorsed prefix, high-water marks, read-only spaces, re-homing and `close`, node placements and the legacy manifests, audiences and server subtraction, pending access and rewrap operations, the author authority check, safety codes, owner requests and the agent revocation flow no longer apply. Those mechanisms are gone, so their findings are closed as **superseded**, not fixed. The Known items below were raised for that design; items 6, 7, 8, 10 and 11 still apply.

## Known items for reviewers

These were raised while drafting. They aren't findings yet; reviewers should confirm, challenge or extend them.

1. **Pairwise safety codes and grinding.** A deterministic 88-bit code invites a two-sided birthday search costing about 2^44 evaluations per side. The design answer is an Argon2id stretch (protocol.md §11.2), with commit-before-reveal left as open question Q1. Reviewers should check the cost estimate. *Round 2:* the server reviewer rechecked it (no finding), and noted the attacker can grind between the second vault's creation and the first comparison; §11.2 now says so.
2. **Server subtraction.** The server may only remove recipients, through an explicit `subtracted` list (§8.4). It can't add them.
3. **`groupSeq` in the access-entry header.** It is there so that a withheld group-membership body is detectable (§6.9).
4. **Envelope v2.** It binds `spaceId` and `authorizedHash` for fork detection (§9.3). `metadata-envelope/v2` mirrors it.
5. **Owner-only anchors.** Only an owner-signed entry anchors the endorsed prefix (§6.7).
6. **Contacts sealed to agents.** The contacts record is sealed to the human and to their enrolled agents (§10.1).
7. **The AD doesn't bind the format version** (§5.1). This is recorded as built: the format is inside the authenticated plaintext.
8. **Lone surrogates.** `TextEncoder` maps them to U+FFFD, so new signed free-text fields must be well-formed (§3.3).
9. **The M1 backfill** trusts the server's tree as it stands at backfill time (§16.2). *Round 1:* S1-7 and M-1 tightened it: the client checks it owns every record, the owner reviews the tree, the genesis commits to legacy manifests, and grant previews list the subtree. The tree itself is still the server's.
10. **KDF floor.** The vault's Argon2id lower bound is libsodium's minimum, which is a hang guard, not a strength floor (§5.6, Q8).
11. **Base64 strictness** of the repo's libsodium decoder (§3.2). Checked on 2026-10-04 with libsodium 1.0.22: it rejects padding, impossible lengths and non-zero trailing bits. Reviewers should confirm that every new byte field goes through this decoder. *Round 1:* the encoding reviewer's probes confirmed it (no finding). Hash fields are now held to `Hash32` text (L2).
12. **BIP-39 word list pinning** (§11.1). The SHA-256 of `english.txt` is **unverified**, because no offline copy was available. PR 2 must record it from the published file and cross-check it.
13. **Safety-code cost figures** (§11.2) come from one machine (EPYC 7401P, about 187 ms native and 245 ms WebAssembly per evaluation). Reviewers should challenge the 10–100× hardware-advantage assumption. *Round 2:* the server reviewer estimated about 2,000 evaluations per second on an H100, about 1.5× cheaper than CPU, so the assumption is conservative (§11.2).
